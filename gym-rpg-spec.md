**Рабочее название:** проект без имени
**Версия документа:** 1.0
**Дата:** 15 августа 2026
**Статус:** спека закрыта, готово к разработке

---

## 1. Суть продукта

Веб-приложение, которое одновременно является:

1. **Серьёзным дневником тренировок** с движком прогрессии нагрузок
2. **RPG-прогрессией**, где статы честно выводятся из реальной проделанной работы
3. **Приватным клубом** на несколько человек с лидербордом и опциональными рейдами на боссов

Ключевой принцип, из которого вытекает всё остальное:

> **Игровой слой измеряет и оценивает тренировки, но никогда не диктует нагрузку.**
> Единственный источник истины о том, что делать сегодня — программа тренировок.

### Целевая аудитория

Автор и его близкий круг (2–5 человек). Не публичный продукт. Следствия:

- Антифрод не нужен — врать в кругу друзей неинтересно
- Но **честность метрик критична**: в маленькой группе искажения заметят за месяц, и цифрам перестанут верить
- RLS обязателен с первого дня — иначе однажды покажешь чужие данные

### Не-цели

- Кардио, бег, растяжка, питание, сон
- Публичная регистрация, монетизация, соцсеть
- Мобильные нативные приложения (PWA достаточно)
- Тренерские функции, планы от ИИ, видеоразбор техники

## 2. Движок очков

### 2.1 Проблема, которую он решает

Наивная метрика «тоннаж» (вес × повторы × подходы) плохая по двум причинам:

1. Награждает много повторов с малым весом
2. Приседания дают в разы больше тоннажа, чем подъём на бицепс, и ноги затапливают все остальные статы

### 2.2 Формула

Каждый подход конвертируется в очки в момент логирования:

```
e1RM_set = weight × (1 + reps / 30)                    -- формула Эпли
e1RM_ref = MAX(e1RM) по (профиль, упражнение) за 90 дней, включая текущий подход
RI       = weight / e1RM_ref                            -- относительная интенсивность

score = reps × RI² × k_effort × 100
```

Множитель усилия по RIR (reps in reserve):

| RIR | k_effort | Комментарий |
|-----|----------|-------------|
| 0   | 0.95     | Отказ — лишний риск без дополнительной пользы |
| 1   | 1.00     | Оптимум |
| 2   | 1.00     | Оптимум |
| 3   | 0.75     | |
| 4   | 0.55     | |
| 5+  | 0.30     | |

**Отсечка:** при `RI < 0.35` очки равны нулю. Это автоматически исключает разминочные подходы, и в UI не нужен отдельный флаг «это разминка».

### 2.3 Почему именно так

- **Присед и подъём на бицепс становятся сравнимы**, потому что каждое упражнение измеряется относительно твоего же предела в нём. Таблица коэффициентов на 800 упражнений не нужна.
- **Разный вес тела и пол перестают быть проблемой.** Участник с жимом 40 кг и участник с жимом 100 кг качают уровень с одинаковой скоростью при одинаковой честности работы. Для приватного круга это критично.
- **Фарм лёгким объёмом математически невыгоден.** Проверка: 5×5 на 80% при RIR 2 = 16.0 очка; 3×12 на 65% при RIR 2 = 15.2; попытка нафармить 4×30 на 30% = 0 (ниже отсечки).
- **Пик награды стоит на RIR 1–2, а не на отказе.** Если максимум поставить на RIR 0, игра будет каждую неделю толкать работать до отказа во всех подходах, и через три месяца пользователь будет травмированным, а не сильным. Награда должна лежать там, где лежит физиологический оптимум.
- **Очки записываются в строку подхода при вставке и никогда не пересчитываются.** Рост рекорда не переписывает историю.

### 2.4 Сырой тоннаж

Не выбрасываем. Живёт как отдельный «сочный» счётчик — «перемещено 412 тонн за всё время», основа для ачивок. На статы не влияет.

## 3. Статы

### 3.1 Набор: 7 статов

Выводятся механически из полей `primaryMuscles` / `secondaryMuscles` базы free-exercise-db. Ручного авторинга нет — только карта «мышца → стат» на 17 строк.

| Стат | Мышцы из БД |
|------|-------------|
| ГРУДЬ | chest |
| СПИНА | lats, middle back, traps |
| ПЛЕЧИ | shoulders, neck |
| РУКИ | biceps, triceps, forearms |
| КВАДРИЦЕПС | quadriceps, calves, abductors, adductors |
| ЗАДНЯЯ ЦЕПЬ | hamstrings, glutes, lower back |
| КОР | abdominals |

**Распределение очков подхода:** 0.7 делится поровну между primary-мышцами, 0.3 — поровну между secondary.

**Почему 7:** при десяти статах на обычном трёх-четырёхдневном сплите половина показателей висит у нуля (задние пучки, предплечья получают только косвенную нагрузку), и аватар вечно светится красным без вины пользователя. Четыре архетипа убивают карту тела, на которой держится аватар. Семь — читаемый семиугольник на радаре, и каждый стат реально набирает объём.

**Про разделение ног:** квадрицепс и задняя цепь разведены намеренно. Это единственный дисбаланс, который встречается почти у всех и реально ведёт к травмам. Одним статом «НОГИ» он маскируется.

### 3.2 Decay: скользящее окно

```
stat_value = SUM(score × вес_мышцы) за последние 28 дней
```

Decay не нужно реализовывать отдельно — он получается бесплатно из оконного запроса. Перестал тренироваться — очки выпадают из окна сами.

### 3.3 Уровни

```
stat_level   = FLOOR(SQRT(stat_value / 40))              -- константа под тюнинг
global_level = FLOOR(SQRT(SUM(all stat_values) / 120))    -- константа под тюнинг
```

Корневая кривая: ранний прогресс быстрый, высокие уровни дорогие. Классическая RPG-подача.

### 3.4 Класс персонажа

Меняется динамически, выводится из распределения статов. Не выбирается пользователем.

Считаем долю каждого стата от суммы. Класс определяется доминирующим паттерном:

| Класс | Условие |
|-------|---------|
| ШТУРМ | грудь + плечи доминируют (жимовой уклон) |
| ТЯГА | спина доминирует |
| ФУНДАМЕНТ | квадрицепс + задняя цепь доминируют |
| БАЛАНС | низкая дисперсия долей — все статы ровные |
| ПЕРЕКОС | один стат больше 35% суммы, либо любой стат ниже 5% |

БАЛАНС — аспирационный класс, его получить труднее всего. ПЕРЕКОС работает как мягкое предупреждение вместо назидательного уведомления.

## 4. Прогрессия нагрузок

Приложение — это в том числе тренировочный дневник, который подсказывает прогрессию.

### 4.1 Алгоритм: двойная прогрессия, гейтированная по RIR

Каждое упражнение в программе имеет цель: подходы × диапазон повторов + целевой RIR. Например 3×8–12 при RIR 2.

После каждого упражнения:

```
все подходы дошли до верха диапазона И медианный RIR ≥ цели
    → +вес, сброс к низу диапазона

верх диапазона достигнут, но медианный RIR < цели
    → держим вес: дошёл на морально-волевых, закрепись

повторы выросли, но не до верха диапазона
    → тот же вес, цель +1 повтор

повторы упали И RIR упал
    → флаг накопленной усталости
```

**Шаг веса:** 2.5 кг для базовых движений низа, 1.25 кг для верха и изоляции, 2 кг для тренажёров со стеком. Настраивается на упражнение.

**Почему не альтернативы:** линейная прогрессия сломается за месяц на среднем и выше уровне. Проценты от 1RM требуют реального тестирования максимума и бессмысленны на изоляции — никто не тестирует 1RM на махах в стороны. Чистая авторегуляция по RIR имеет известную болезнь: люди систематически завышают запас, «RIR 2» на деле часто RIR 0. Здесь объективное правило ведёт, RIR служит гейтом, а тренд e1RM работает аудитором.

### 4.2 Аудит калибровки RIR

Фича-дифференциатор, данные для которой уже лежат в базе.

Сравниваем заявленный RIR с фактическим падением повторов между подходами на одном весе. Если пользователь пишет RIR 2, а в следующем подходе повторы падают на 3+ — запаса не было.

Показываем в дневнике: «ты недооцениваешь запас в среднем на 1.5 повтора». Такого почти ни у кого нет.

### 4.3 Определение застоя

Триггер (по выбору пользователя система только предупреждает, решение за ним):

- Тренд e1RM по упражнению не растёт 3 сессии подряд, **либо**
- Дважды не выполнен целевой диапазон повторов на одном весе

**Подача: карточка-инсайт в дневнике, не модальное окно посреди тренировки.**

### 4.4 Циклы

Разгрузка не по календарю, а **по сигналам усталости** — управляется показателем готовности (раздел 5).

## 5. Готовность

Показатель 0–100, пересчитывается ежедневно через pg_cron. Используется как гейт для рейдов и как триггер разгрузки.

Компоненты (константы под тюнинг на живых данных):

```
readiness = 100
  − 25 × (падение среднего RIR за 7 дней относительно 28-дневной базы)
  − 25 × (падение тренда e1RM по базовым упражнениям)
  − 20 × (превышение объёма за 7 дней над 28-дневной нормой)
  + 15 × (бонус за дни отдыха, максимум при 2–3 днях)
```

Ограничение диапазона 0–100.

| Готовность | Поведение |
|------------|-----------|
| > 70 | Доступны боссы высокого тира, лучшая добыча |
| 40–70 | Доступны обычные боссы |
| < 40 | Рейды закрыты. Приложение предлагает разгрузочную неделю |

Смысл формулировки: система не читает морали, она просто закрывает ворота. «Рейд недоступен, вернись через два дня» вместо «ты перетренировался, отдохни».

## 6. Рейды

### 6.1 Базовая модель

**Рейд добровольный.** Обычная тренировка не является боем. Пользователь сам решает, когда войти.

**Один рейд = одна тренировка = один бой.** Начал сессию в режиме рейда — вся её работа идёт в урон.

### 6.2 HP босса

```
HP = средний score сессии за последние 28 дней × множитель тира
```

Множители: 1.10 / 1.25 / 1.40 для трёх тиров сложности.

Чтобы убить босса, нужно отработать заметно выше своей же нормы за месяц. Это делает рейды двигателем прогрессивной перегрузки, а не статичным контентом, который устареет.

**Кооп:** HP суммирует базовые линии всех участников, иначе бой вдвоём становится вдвое легче.

### 6.3 Механики боссов

Механики диктуют **качество** работы, а не только количество. Задаются в `bosses.mechanics` как JSONB.

| Механика | Эффект | Что провоцирует |
|----------|--------|-----------------|
| Броня | Урон наносят только подходы с RI > 0.8 | Неделя тяжёлой работы |
| Фазы | Броня спадает по мере падения HP | Правильный порядок: базовые тяжёлые первыми, добивка потом |
| Иммунитет к стату | Урон от выбранного стата = 0 | Принудительный акцент на отстающее |
| Спящий | Наносит урон себе только при малом объёме и высокой интенсивности | **Разгрузочный босс** |

### 6.4 Разгрузочный босс — обязательная механика

Система, которая каждый цикл требует объёма больше предыдущего, за полгода приводит к перетренированности или травме.

«Спящий» побеждается **малым** объёмом при высокой интенсивности. Появляется при готовности 40–55. Без этого элемента механика рейдов будет работать против пользователя.

### 6.5 Кооп-рейды: только синхронно

Кооп доступен, только когда участники тренируются вместе физически.

1. Один открывает рейд в режиме кооп
2. Остальные из круга получают приглашение и присоединяются в течение 15 минут
3. HP = сумма базовых линий участников × множитель тира
4. Урон каждого виден остальным в реальном времени (Supabase Realtime)

Так кооп остаётся редким событием — тем, чем и должен быть.

### 6.6 Экономика: жетоны

Валюта входа — **не очки статов**, а жетоны за дисциплину.

- Выполнил запланированную по программе тренировку → +1 жетон
- Вход в рейд стоит жетоны в зависимости от тира
- **При провале жетоны и добыча сгорают**

Смысл: рейдить может только тот, кто стабильно ходит. Настоящая валюта в зале — регулярность, не сила, и экономика это отражает.

### 6.7 Добыча

| Награда | Механика |
|---------|----------|
| Косметика для аватара | Скины, элементы экзоскелета, эффекты |
| Титулы и трофеи | Отображаются в профиле и лидерборде |
| Доступ к контенту | Новые тиры боссов, новые механики |
| **Якорь стата** | Часть очков в 28-дневном окне защищена от decay ещё 2 недели |

### 6.8 Про «ускорение роста статов» — почему заменено на якоря

Прямые множители к статам ломают статы как измерение. Весь смысл нормализации по RI и RIR в том, чтобы стат честно отражал работу. Если рейды накручивают статы, лидерборд начинает показывать не «кто больше тренировался», а «кто чаще рейдил».

**Якорь даёт то же ощущение честно:** стат держится выше за счёт замедленного decay, но ни одного фальшивого очка в систему не попало. И это идеально стыкуется с механикой скользящего окна.

## 7. Квесты

Недельные, генерируются автоматически (pg_cron, ночь воскресенья).

Источник целей — история пользователя, а не константы:

- «Набери 110% объёма прошлой недели по стату ЗАДНЯЯ ЦЕПЬ»
- «Три сессии на этой неделе»
- «Побей e1RM в жиме лёжа»
- «Ни одного подхода с RIR 0» — квест на техничность
- «Выровняй ПЕРЕКОС: доведи отстающий стат до 12% суммы»

Награда — жетоны и небольшая косметика.

---

## 8. Круг и лидерборд

- **Вход по ссылке-инвайту.** Владелец круга генерирует токен, ссылка одноразовая или с TTL
- Лидерборд по глобальному уровню, с возможностью переключения на отдельные статы
- Видны профили участников: аватар, класс, статы, титулы, стрик, последняя активность
- Метрики нормализованы (раздел 2.3), поэтому сравнение честное независимо от веса тела и пола

## 9. UX

### 9.1 Два режима громкости

Главное решение по подаче игрового слоя.

**Обычная тренировка — игры почти не видно.**
- Экран: весь список упражнений сессии сразу, не по одному
- Веса и повторы предзаполнены из прошлого раза
- После подхода — максимум тонкая цифра очков в углу
- Полный разбор на итоговом экране: прирост статов, изменение уровня, инсайты дневника, калибровка RIR

**Рейд — всё живое.**
- HP босса на экране, полоска ползёт
- Урон всплывает после каждого подхода
- Механики босса видны и подсвечены
- В коопе — урон партнёра в реальном времени

**Почему контраст:** если анимация урона всплывает после каждого подхода всегда, к третьей неделе это визуальный шум, который хочется отключить. Тихие обычные тренировки делают рейд событием — то же приложение, но с включённым звуком.

### 9.2 Логирование в зале

Ключевой сценарий: форма, которую заполняют потными руками, стоя у стойки, между подходами.

1. Пользователь стартует день программы
2. Все упражнения уже в списке, веса и повторы предзаполнены значениями прошлой сессии
3. Меняется только то, что изменилось
4. RIR указывается на каждый подход — компактный степпер 0–5
5. Логирование происходит прямо во время тренировки, между подходами

Требования: крупные тач-таргеты, ввод одной рукой, тёмная тема, никаких модальных окон в процессе.

### 9.3 Аватар

**Первичная визуальная метафора.** SVG-силуэт тела, мышечные группы — отдельные `path`, цвет и свечение задаются уровнем соответствующего стата. Тепловая карта, читаемая за полсекунды.

В киберпанк-эстетике читается как биосканер — стилистика попадает в природу приложения, которое по сути является телеметрией.

Никакого Blender для MVP. Рендер-арт можно подставить позже, если захочется.

### 9.4 Дерево навыков — вторая фаза

Дерево навыков это **контентная система**, а не визуализация. Узлы должны реально что-то давать: доступ к типам боссов, новые механики, слоты квестов, модификаторы якорей. Пока не видно на живых данных, как ведут себя статы, половина узлов будет спроектирована мимо.

### 9.5 Стиль

Sci-fi / киберпанк. HUD-эстетика, телеметрия, моноширинные акценты на цифрах. Босс — дрон, ИИ-протокол, боевая система, а не дракон, которому в спортзале взяться неоткуда.

**Язык интерфейса: только русский.**

## 10. Технический стек

### 10.1 Фронтенд: Vite + React + TypeScript, PWA

**Почему не Flutter Web,** несмотря на то что автор в нём быстрее: основной сценарий — форма, заполняемая на телефоне в зале. Нативные веб-инпуты, поведение мобильной клавиатуры и инерция скролла здесь важнее скорости разработки, а CanvasKit добавляет пару мегабайт к первой загрузке. SVG-аватар, графики дневника и анимации урона — ровно то, для чего создан браузер.

**Почему не Next.js:** SEO у приватного приложения нет, а Supabase закрывает бэкенд целиком. Статический SPA на Vercel достаточно.

Библиотеки:

| Задача | Решение |
|--------|---------|
| Состояние и запросы | TanStack Query |
| Графики дневника | Recharts |
| Анимации рейда | Framer Motion |
| Аватар | Рукописный SVG с path на мышечную группу |

### 10.2 Бэкенд: Supabase

- **Postgres** — данные и вся логика счёта
- **Auth** — magic link, инвайты по токену
- **RLS с первого дня** — обязательно
- **Realtime** — синхронные кооп-рейды
- **Edge Functions + pg_cron** — пересчёт готовности, истечение якорей, генерация квестов

### 10.3 Логика счёта живёт в Postgres

`score` считается триггером `BEFORE INSERT` на таблице `sets` и записывается в строку.

**Почему в SQL, а не на клиенте:** очки не должны разъезжаться между клиентами и не должны пересчитываться задним числом. Статы — оконный запрос по 28 дням, decay получается бесплатно. Postgres здесь сильнее любого клиентского кода.

### 10.4 Офлайн

Полноценный offline-first избыточен, связь в зале есть. Но нужны **оптимистичные мутации с очередью в localStorage** — примерно полчаса работы.

Не ради подвалов без связи, а потому что единственный потерянный подход посреди тренировки — это тот случай, когда пользователь закрывает приложение и не возвращается.

## 12. План сборки

Порядок диктуется **данными, а не дисциплиной**: рейды физически нельзя настроить в первую неделю, потому что HP считается от средней сессии за 28 дней. Пока истории нет, босс будет либо умирать от одного упражнения, либо бессмертным. То же с лидербордом и decay.

| Фаза | Срок | Содержание |
|------|------|------------|
| **1** | Недели 1–2 | Auth, схема БД, импорт free-exercise-db, карта мышца→стат, конструктор программ, экран логирования с автозаполнением и RIR |
| **2** | Недели 2–3 | Триггер score, статы, уровни, класс, SVG-аватар, дневник, движок прогрессии, детектор застоя |
| **3** | Недели 3–4 | Круг, инвайты, RLS-политики, лидерборд. Остальные участники начинают набирать историю |
| **4** | Недели 4–5 | Готовность, жетоны, недельные квесты, аудит калибровки RIR |
| **5** | Неделя 5+ | Рейды на живых откалиброванных цифрах: соло, механики, добыча, якоря |
| **6** | Позже | Кооп-рейды через Realtime, дерево навыков, косметика |

Код рейдов можно писать параллельно с фазами 3–4, но включать раньше месяца накопленных данных бессмысленно.

## 13. Константы под тюнинг

Всё это цифры, взятые из здравого смысла, а не из данных. Ожидай, что половину придётся крутить после первого месяца использования:

- Показатель степени `RI²` в формуле score
- Отсечка `RI < 0.35`
- Таблица `k_effort` по RIR
- Окно `e1RM_ref` = 90 дней
- Окно статов = 28 дней
- Делители кривой уровней (40 и 120)
- Все веса в формуле готовности
- Множители тиров HP (1.10 / 1.25 / 1.40)
- Пороги готовности для гейтов рейдов
- Пропорция 0.7 / 0.3 между primary и secondary мышцами
- Порог ПЕРЕКОСА (35% и 5%)

**Рекомендация:** держать их в одной таблице `game_config` в Postgres, а не разбрасывать по коду. Иначе тюнинг превратится в поиск магических чисел по репозиторию.

## 14. Решённые риски

| Риск | Решение |
|------|---------|
| Метрика тянет тренировки в сторону лёгкого объёма | Нормализация по RI, отсечка на 35% |
| Ноги затапливают все статы | Относительная интенсивность вместо тоннажа |
| Разный вес тела и пол делают лидерборд бессмысленным | Каждый измеряется относительно себя |
| Игра толкает работать до отказа | Пик `k_effort` на RIR 1–2, штраф на RIR 0 |
| Рейды каждый цикл требуют больше объёма → травма | Разгрузочный босс «Спящий», гейт по готовности |
| Босс и движок прогрессии дают противоречивые указания | Рейды добровольные; план — единственный источник истины |
| Награды за рейды инфлируют статы | Якоря против decay вместо множителей |
| Игровая отдача превращается в шум | Два режима громкости: тихая тренировка, громкий рейд |
| Потерянный подход из-за связи | Оптимистичные мутации с очередью |
| Утечка данных в приватном круге | RLS с первого дня |

## 15. Открытые вопросы для второй итерации

Не блокируют разработку, но потребуют решения:

1. Трекинг веса тела — нужен ли, и влияет ли он на что-то кроме графика
2. Push-уведомления: напоминания о тренировке, приглашения в кооп-рейд
3. Структура дерева навыков и что конкретно дают узлы
4. Ачивки: полный список и условия
5. Экспорт истории (CSV) — на случай миграции
6. Что происходит при смене программы посреди цикла
7. Упражнения с весом тела и с дополнительным отягощением: как считать `weight` для подтягиваний
8. Односторонние упражнения: считать за подход или за два
