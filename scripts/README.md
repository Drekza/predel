# scripts/

Служебные скрипты сборки. Запускаются вручную, в рантайм приложения не попадают.
Всё под Node 20+, ESM, без зависимостей — только стандартная библиотека.

## build-exercise-seed.mjs

Собирает сид справочника упражнений.

```bash
npm run seed:build          # == node scripts/build-exercise-seed.mjs
```

Скрипт детерминированный: одинаковый вход даёт побайтово одинаковый выход
(строки отсортированы по slug, словарь — по ключу, даты генерации в файле нет).
Поэтому перегенерация без изменения данных не даёт diff.

### Вход (в репозитории, руками не редактируется)

| Файл | Что это |
|------|---------|
| `data/exercises.json` | дамп [free-exercise-db](https://github.com/yuhonas/free-exercise-db), 873 объекта, лицензия Unlicense |
| `data/exercises.extra.json` | 3 кардио-упражнения, дописанные вручную: `Outdoor_Running`, `Outdoor_Walking`, `Assault_Bike` |
| `data/en/chunk-01..10.json` | исходные английские названия, разбитые на чанки — материал для перевода |
| `data/ru/chunk-01..10.json` | результат перевода: `id -> русское название`. Чанки 01–09 — 675 силовых, чанк 10 — 17 кардио |

Отсутствующий чанк `ru/*` не роняет сборку: скрипт печатает `[warn]`, а упражнения
без перевода уезжают в сид с английским именем в `name_ru`. Список таких id виден
в сводке (топ-10). Это фолбэк на аварию, а не рабочий режим — перед коммитом сида
`без перевода` должно быть `0`.

### Выход

| Файл | Что это |
|------|---------|
| `data/exercises.ru.json` | склеенные и отсортированные переводы; удобно смотреть diff словаря целиком |
| `../supabase/seed/0002_exercises.sql` | сид, коммитится в репозиторий |

### Что делает

1. Склеивает `exercises.json` + `exercises.extra.json`, оставляет категории
   `strength`, `powerlifting`, `olympic weightlifting`, `strongman`, `cardio`.
   Ожидается ровно **675 силовых + 17 кардио = 692**. Не сошлось — падает.
2. `kind` = `cardio` при `category === 'cardio'`, иначе `strength`.
3. `slug` = поле `id` датасета в нижнем регистре, всё не `[a-z0-9]` схлопнуто в один
   дефис. Уникальность проверяется, коллизия — падение.
4. `weight_step_kg` по правилу из спеки 4.1:
   `machine`/`cable` → **2.00**; иначе `mechanic = compound` и есть пересечение
   `primaryMuscles` с низом тела (quadriceps, hamstrings, glutes, lower back,
   calves, abductors, adductors) → **2.50**; иначе → **1.25**.
   У кардио всегда 1.25 — поле не используется.
5. Пишет SQL: `begin;` + 7 батчей `insert ... values` по 100 строк с
   `on conflict (slug) where owner_id is null do update set ...` + `commit;`.

### Проверки, на которых скрипт падает

- количество после фильтрации ≠ 675 + 17;
- мышца в `primaryMuscles`/`secondaryMuscles` вне 17 известных значений
  (это ключи `public.muscle_stat_map`, лишнее значение молча обнулило бы стат);
- коллизия `slug`;
- битый JSON, пустой перевод, отсутствие `id` или `name`.

Выход с кодом 1 и русским сообщением, файлы при этом не переписываются.

### Про кардио

17 строк с `kind = 'cardio'` сохраняют мышцы из датасета — они нужны только для
фильтров в списке упражнений. В игровой слой кардио не попадает никогда: очков не
даёт, статы и тоннаж не трогает. Гарантия на стороне БД — триггер расчёта `score`
(фаза 2) пропускает строки `sets` с `kind = 'cardio'`, у них `score` остаётся `null`.

Подробности — [`../docs/exercises.md`](../docs/exercises.md).

## Как накатить сид

Сам скрипт в базу не ходит и переменных окружения не читает.

```bash
npm run seed:build
psql "$DATABASE_URL" -f supabase/seed/0002_exercises.sql
```

Либо целиком через точку входа `supabase/seed.sql` (там подключены оба сида),
либо `npx supabase db reset` — пути перечислены в `supabase/config.toml`.
Файл идемпотентен: повторный запуск обновляет справочные поля глобальных
упражнений, не создаёт дублей, не трогает кастомные упражнения пользователей и
не ломает внешние ключи из `program_items` и `sets` (`id` строк не меняется).
